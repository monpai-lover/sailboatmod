# Aeronautics 船舶／陆地载具注册控制方块设计

状态：供用户确认的设计稿，尚未实现。目标环境：Minecraft 1.21.1 NeoForge；本机 Aeronautics 1.3.2、Simulated 1.3.2、Offroad、Sable 2.0.6、Create 6.0.10。

## 用户要求

- 已物理化的航空学船只可以登记为 Sailboat 物流载具，使用自动航行、码头、货舱和运单。
- 陆地物理载具有独立的注册方块，接入道路导航和陆运。
- 两种注册控制方块均登记为 **0 质量**。
- 保留实际物理载具、原生动力和碰撞；物流继续采用当前托管、运单、交付权威。

## 方块与玩家流程

船用方块：`sailboatmod:vessel_registration_controller`，显示名“船舶注册控制器”。
陆用方块：`sailboatmod:land_vehicle_registration_controller`，显示名“陆运注册控制器”。

放置在实际结构上，物理化后打开 LDLib2 面板，读取所属结构、朝向与尺寸。玩家填写名称，指定本船／本车参与物流的货舱，设置动力信号端口，绑定码头或驿站，再执行登记。未物理化时可预配置，完成组装后才能成为可调度载具。一个物理结构同时只允许一个控制器处于启用状态；多个控制器需要选出一个，其余保持停用。

面板使用共同的状态、登记、货舱、航线／道路、控制通道页。状态区显示未组装、待登记、空闲、执行任务、等待地形、人工接管、故障及未加载。实际动力或转向配置不完整时，允许保存登记资料，但禁止自动发车／启航，并指出缺少的通道。

## 方案选择

推荐原生动力控制：控制器输出可配置的油门、制动、转向与倒挡信号，仍由玩家已经建好的发动机、Create 传动、螺旋桨、轮胎等产生真实动力。它需要一次端口配置，能保留动力、燃料、质量和碰撞规则。

直接物理冲量控制也是可行方案，但控制方块将同时成为推进器，需要另行决定推力和能耗。第一版不默认提供这种额外动力。

仅登记并跟踪人工驾驶载具可作为调试模式，不能代替用户要求的自动航行与物流。第一版验收必须包括自动运输。

## 原生控制契约

船用控制器提供前进油门、后退／倒挡、左转、右转、停止通道。通过方块朝向定义船首，将世界航点转到船体局部坐标计算航向误差。玩家可将转向信号接到现有舵、动力差分或其他实际转向组件。控制器不会假设所有船都存在一个统一的 `setThrottle/setRudder` 方法。

陆用控制器提供油门、刹车、倒挡、左转、右转通道。已核实 Offroad 轮座两侧红石差对应约 ±30°转向，上方红石控制刹车；满刹车切断轮胎驱动项并增加阻尼。驱动读取 Create 有符号转速，倒车通过传动反向完成。制动是实际物理减速。

Simulated 的 `ThrottleLeverBlockEntity.setSignal(int)`、`SteeringWheelBlockEntity.updateTargetAngle(float)` 可作为可选的明确绑定控件。Analog Transmission 的调速方向取决于动力输入端：15 断开，0 为 1:1；端口配置必须标明布线拓扑并支持反相校准。Directional Gearshift 的正转侧单独通电为正转，反转侧单独通电为反转，两侧同时／均无信号为断开。原生导航桌的 `NavigationTarget` 可为路线书提供单航点方位兼容，但多航点、避障、到港仍由本模组管理。

人工接管后自动输出停止；继续任务需要明确恢复。地形尚未就绪、传动／舵失效、停靠目标失效时进入等待或故障状态，不推进任务完成状态。

## 物理对象身份与坐标

控制器 NBT 保存独立 `registrationUUID`、所有者、类型、货舱局部位置、信号配置、终端绑定和任务引用。Sable SubLevel UUID 是当前物理结构绑定，不作为永久业务身份。

可选兼容层使用实际的 `Sable.HELPER.getContaining(level, blockPos/blockEntity)` 解析归属，使用容器 `getSubLevel(UUID)` 恢复已知绑定。位置采用 `logicalPose().transformPosition(...)`；方向采用姿态的法向转换，世界目标以逆变换进入局部空间。绝不把内部 plot 方块坐标登记为外部世界码头坐标。

卸载时记录“未加载”，保留运单；明确移除或结构分裂时停止控制并重新解析控制器归属、货舱和尺寸。控制器和货舱分到不同结构后不能继续将原货舱当作可用库存。重新组装和服务器重启都按同一个登记身份恢复，恢复前检查唯一性与绑定。

## 质量 0 的准确注册

Sable 内置 `data/sable/physics_block_properties/weightless.json` 已使用 `sable:mass: 0.0`。两个方块各提供一个本模组的 `physics_block_properties` 定义，显式 selector 对准方块，优先级 2000 高于普通默认规则 1000：

```json
{
  "priority": 2000,
  "selector": "sailboatmod:vessel_registration_controller",
  "properties": { "sable:mass": 0.0 }
}
```

陆用文件将 selector 改为 `sailboatmod:land_vehicle_registration_controller`。验证读取到的实际质量确实为 0；不把质量改成极小正数。质量 0 对正常船体的质量和惯量贡献均为 0；体积是另一项属性，本次不额外改动。

登记及启用要求整个结构有正总质量。Sable 对孤立的全零质量分裂结构可能移除其方块，应按实际移除处理登记和任务，不能让任务继续行驶或误报到港。

## 共同运输边界

保留现有 `TransportEntity` 对 Sailboat／Carriage 的兼容入口，抽出不强制转换成 Minecraft `Entity` 的窄接口：

- `TransportRef`：提供方、登记 UUID、维度与当前物理绑定。
- `LogisticsCarrier`：名称、授权、世界位置、状态、运单及真实货舱。
- `CargoPort`：指定 `IItemHandler` 的容量模拟、装卸和本次交易收据。
- `NavigationPort`：提交现有世界航点，读取真实速度、航点进度、停止／到达结果。

码头／驿站发现统一合并实体载具与已登记物理载具，并用实时世界位置检查装卸范围。引用与网络包逐步兼容旧实体 ID 和新稳定载具引用。轨迹清理通过载具解析器区分未加载和损毁，不再仅凭 `server.getEntity(uuid)==null` 删除物理载具。

货物只存在于登记的真实货舱，不在登记 SavedData 中再存一份。个人箱子不自动加入物流。现有上架已扣仓库库存，调度只兑现保留数量；适配层不得再次从源仓扣货。装载、路线启动、运单转入运输、到港交付和托管结算复用当前流程。失败回滚只撤销本次收据记录的货物，不能清空整船／整车个人库存。

## 导航与沿途生成

船舶复用现有 NBT 优先、Tellus 预测回退的水路规划和前瞻校验；道路载具复用道路航点和施工后的真实道路。规划参数必须使用登记载具的尺寸、吃水／离地间隙、转向及制动能力，不能照搬小帆船的固定半宽。远端只作为预测，近处真实障碍校验有权停止和请求局部重规划。

现有船只与马车已有滚动区块窗口，但新控制器须增加 Sable 自身的 SubLevel 加载票据和沿途世界区块票据，并释放窗口外票据。大范围 Tellus／道路流式规划和道路、Town、Nation 的预测底图是独立后续工作；注册方块不宣称已解除现有约 12,288 格水路搜索及道路预览限制。

## 验收

- 两种方块在实际 Aeronautics/Sable 中均读到质量 0；主模组在不安装这些可选模组时正常加载。
- 真实组装／拆解／分裂／卸载／重启后不重复登记，不把内部存储坐标当作世界坐标。
- 有原生动力的船可逐航点转弯、制动、停靠；Offroad 车可转向、刹车及倒车，手动接管立即生效。
- 未配置动力时不接受自动调度；不可用或未加载期间不把运单误判为交付或遗失。
- 船和陆运各完成一笔实际装货、途中运行、交付与付款；途中停止和启动失败不复制货物、不清个人库存。
- 大船／长车按自身尺寸避障，不沿用小船固定宽度；冷区块等待时保留任务并正确停驶。

接口与字节码证据位于未入库的 `build/physical-vehicle-audit-20261029/`。本设计未将任何实现或游戏测试结果标记为已完成。
