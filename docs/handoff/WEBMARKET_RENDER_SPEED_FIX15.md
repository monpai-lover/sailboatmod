# WebMarket fix_15：渲染速度与出图延迟

本次在 fix_14 的服务器负载限制上继续提速。只更新服务器 WebMarket 附属，使用相同主模组 API 和网络协议；已正常运行上一版附属的服务器无需更新客户端。保留原地图缓存。

## 安装和控制

停止服务器，移出旧 WebMarket 附属，再放入 `sailboatmod-marketweb-1.3.13-fix_15-neoforge-1.21.1.jar`，只保留一个附属 JAR。刷新网页使新脚本生效。

```text
/marketweb map pause
/marketweb map resume
/marketweb map status
```

仍使用 `config/sailboatmod-marketweb-common.toml`，默认共享 2ms 软预算、每 tick 最多 8 次捕获和 4 次 probe、一个绘图线程。没有靠增加这些上限获得下列基准结果。

## 改动

- PNG 读取和编码使用局部内存流，避免每张小图创建 ImageIO 临时文件。保持原有无损压缩参数、像素及 PNG 文件大小，不修改其他模组共享的 ImageIO 全局设置。
- 增加总计 32MiB 的解码像素缓存，按实际压缩文件字节校验，不只依赖时间戳。外部改图、删除重建、世界切换都不会取错缓存；返回的数组可以独立修改。未变化的直接写入可跳过编码。
- 小批数据约每 5 tick（正常 20 TPS 时 250ms）推进和检查刷新，避免等待整个后台队列空闲。每个区域仍有限频和背压，恢复进度保存保持较低频率并在停服强制保存。旧 `webMapBackgroundIntervalTicks` 控制恢复检查点节奏，不再阻塞小批出图。
- 周期扫描已经知道某区域实际保存的区块，就只访问这些位置，不把稀疏区域重新展开成全部 1024 个候选。
- 全图渲染期间，剩余预算可处理少量附近已加载区块；避开正在累计旧快照的同一区域，防止新图被旧快照覆盖。前台候选有独立索引和最多 64 个额外位置，每 tick 检查有上限；已卸载的前台任务可移交到有上限的恢复积压，保留待处理工作。
- 网页的地形变更检查独立为 2 秒，打开或回到可见立即检查；市场元数据仍保持 30 秒。隐藏和关闭时停止相关请求，回来继续处理保留任务。

## 实测范围

使用现有存档的一张 512×512 地形瓦片及其四级缩略图，交错启动每版 3 个独立 JVM；每个场景每次 JVM 预热 2 次，合计每版 11 次计时。构造输入、复制文件、像素校验均不计入渲染耗时。文件系统缓存为热状态；表内另行区分解码缓存是否已命中。

| 场景 | fix_14 中位耗时 | fix_15 中位耗时 | 倍率 |
|---|---:|---:|---:|
| 同一区域连续 32 批局部更新 | 3376.1ms | 1601.1ms | 2.11× |
| 解码缓存命中的单区块更新 | 101.7ms | 52.5ms | 1.94× |
| 解码缓存命中的未变化单区块 | 41.8ms | 1.60ms | 26.09× |
| 完整区域首次写入 | 59.5ms | 48.2ms | 1.23× |

所有样本逐项比较了五层像素 SHA256、PNG 数量、文件字节数和是否有变更，结果一致。更快的未变化场景仍包含读取当前文件字节和完整像素比较，并非只测一个空操作。原始 CSV、全部场景（含未改动的着色路径）及分配量对比随包提供。

这些是本机、该瓦片和该工作负载的渲染管线数据，不是生产服 TPS、所有地形或 Tellus 预测采样的通用倍数。首次填充解码缓存要保存额外数组副本，常驻缓存上限为 32MiB；实际收益取决于连续更新的复用程度。

同类项目及准确源码版本见 [渲染参考](WEBMAP_RENDER_SPEED_REFERENCES_20261104.md)。采用的机制自行实现，没有引入新的第三方库。
