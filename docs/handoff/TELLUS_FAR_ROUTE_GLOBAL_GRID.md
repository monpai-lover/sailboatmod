# Tellus far routes: global water grid, offshore legs, reuse and destination UI

Base: `feat/destination-route-network` (ada8242b). Network protocol 21: update server and clients together.

## Why

Taipei -> Amsterdam on a Tellus 1:100 world timed out after 150 s in the coarse phase
(`分层规划停止 reason=TIMEOUT step=128 节点=5739`): every coarse sample went through the async
NBT probe plus a full native `samplePreloadTerrain` (elevation + land cover), throttled to 16 in flight.

## What changed

- `GlobalWaterGridPlanner`: Tellus far routes plan their guidance on a 16-128 block water grid sampled from
  Tellus' own land mask (`TellusLandMaskSampler`, the data `samplePreloadTerrain` uses for land/sea; coarse
  cells use coarser mask zooms; neighbouring tiles are prefetched in parallel). Bidirectional weighted A*;
  either frontier exhausting = enclosed at that cell size, so it moves to a finer cell instead of flooding.
- Heuristic: sea distance from a bundled 75 KB world overview (`world_water_overview.bin.gz`, generated by
  `tools/gen_world_water_overview.py` from Natural Earth, public domain). Graph nodes are per-cell local
  water components, so it cannot leak across isthmuses (Suez). Heuristic only; navigability is always the mask.
- Legs: the grid path is string-pulled; open-water legs with 24-block (minimum 4) clearance are used as-is,
  the rest and both port ends go through the existing detailed hull-checked search. Coast-adjacent grid cells
  cost extra, so lanes keep off the shore where the sea allows.
- Mid-route detailed chunks (>1024 blocks from both ports) are predicted from the land mask
  (`SurfaceSamplerPredictor`); ports keep the generator prediction. Top water block = sea level - 1.
- Post-processing (`finishGuidedRoute`): only non-direct sections are re-finished; direct legs near ports
  are strictly hull-checked first, else the whole route falls back to full post-processing. Offshore target
  12 blocks, max shift 32. Budgets scale with route length.
- Reuse: reused legs are revalidated with mask predictions (seconds, not a 60 s timeout); only 256 blocks
  either side of reuse/gap joints are re-finished.

## UI / protocol 21

- Dock tab "派遣" is now "前往目的地" (go to destination: pick ship and port; routing is automatic).
- "航线" tab keeps stored-route management. Both pickers have 规划方式: 最优航线 (fresh optimal plan,
  default when creating a stored route) / 优先复用 (reuse stored lanes, plan only gaps, default for
  destinations). `CreateAutoRoutePacket` and `DepartForDestinationPacket` carry the preference.

## Validation (offline, real Tellus land mask, 1:100)

- Taipei -> Amsterdam: 10.6 s, 279k blocks via Malacca and the Cape, 0 land crossings,
  0.2 % of open-sea route within 8 blocks of land. With 300 ms per tile download (sequential): 64.7 s.
- Taipei -> Singapore: fresh 1.3 s; reusing the stored Amsterdam route 0.75 s (1.3 % longer).
- Benchmark: `SAILBOAT_TELLUS_LANDMASK=/path/tellus_landmask.pmtiles ./gradlew test --tests '*TellusTaipeiAmsterdam*'`
  (optional `SAILBOAT_TELLUS_TILE_MILLIS`, `SAILBOAT_TELLUS_ROUTE_OUT`).
- Not run on a live Tellus server. `MarketLiveUpdatePacketTest.registeredLastAsAClientboundPayload` already
  fails on the base branch (packet order) and is unchanged here.
